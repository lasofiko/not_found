# FloCast

Продукт команды **Not Found** — исследовательский прототип для анализа грузовых перевозок и транспортных сценариев. Интерфейс поддерживает три коридора: **Калининградская область, Приморский край и Камчатский край ↔ остальная Россия**. Направления `inbound` (в исследуемый регион) и `outbound` (из региона) рассматриваются отдельно.

Это не production-система и не готовый прогнозный сервис. Полного подтверждённого целевого ряда коридора по направлениям, видам транспорта и группам грузов нет. Наблюдения (`observed`), оценки (`estimated`), синтетические примеры (`synthetic`), прогнозы (`forecast`) и сценарные расчёты (`scenario`) не взаимозаменяемы.

## Что уже работает

- **Калькулятор мощности** на `/` и `/capacity`: считает чувствительность дефицита к введённым пользователем нагрузке, доступной и дополнительной мощности через `POST /api/v1/scenarios/capacity`. География и грузопоток из данных не подставляются.
- **React + TypeScript + Vite-демо** на `/dashboard/`: фильтры географии и направления, графики, выгрузка CSV и панель ассистента. Все числовые примеры синтетические, включая значения за 2025 год; модель не вызывается.
- **Инфраструктурный API**: `health`, `config`, `status`; OpenAPI и Swagger доступны на `/openapi.json` и `/docs`.
- **Необязательный серверный LLM-ассистент**: интерпретирует JSON-контекст через настроенного OpenAI-compatible провайдера, не получая ключ в браузере.
- **ETL и ML-эксперименты**: запускаются отдельно от HTTP-приложения и требуют локального комплекта данных.

Числовое React-демо доступно только для прежнего агрегированного примера морского пересечения Калининградской области. Для Приморья, Камчатки и городской детализации интерфейс показывает отсутствие данных, а не нулевой или заимствованный объём. Поддержка коридора в справочнике не означает наличие наблюдений, расчётов или модели для него.

Пока не подключены утверждённый полноценный целевой ряд, прогнозный HTTP API и отображение результата ML в основном интерфейсе. В Git нет готовых модельных артефактов; наличие кода в `ml/` не подтверждает обучение, точность или готовность интеграции. Два действия в React-демо являются иллюстрациями, а не утверждёнными сценариями команды.

## Быстрый запуск

Команды выполняются из корня репозитория. Для backend нужен **Python 3.11+**. Для React-сборки дополнительно нужны Node.js с версией из `frontend/package.json` — **`^22.12.0 || >=24.0.0`** — и npm. Данные, ML и Jupyter для минимального запуска не нужны.

### Backend и калькулятор

macOS / Linux:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e ".[dev]"
test -e .env || cp .env.example .env
uvicorn backend.app:app --reload
```

Windows PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev]"
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
uvicorn backend.app:app --reload
```

Если `.venv` или `.env` уже существуют, не создавайте их заново. В новом терминале достаточно активировать окружение. Копирование выше не перезаписывает существующий `.env`.

После запуска доступны:

- `http://127.0.0.1:8000/` и `http://127.0.0.1:8000/capacity` — калькулятор;
- `http://127.0.0.1:8000/docs` — Swagger UI;
- `http://127.0.0.1:8000/dashboard/` — React-демо, но только после сборки; без неё backend возвращает HTTP 503 с инструкцией.

### Собранное React-демо

В другом терминале из корня проекта:

```bash
npm --prefix frontend ci --ignore-scripts
npm --prefix frontend run build
```

Перезапустите backend после появления `frontend/dist/index.html`: состав маршрутов определяется при создании FastAPI-приложения. Затем откройте `http://127.0.0.1:8000/dashboard/`.

### Разработка через Vite

При запущенном backend:

```bash
npm --prefix frontend run dev
```

Откройте `http://localhost:5173/dashboard/`. Vite проксирует `/capacity`, `/app.js`, `/config.json` и текущий `BB_API_PREFIX` на backend. Адрес по умолчанию — `http://127.0.0.1:8000`; его меняет `BB_DEV_BACKEND_URL` в корневом `.env` или окружении. После изменения настроек перезапустите Vite. Синтетическое демо отображается и без backend, но калькулятору и ассистенту API необходим.

### Отдельный статический калькулятор

Этот вариант относится только к `capacity.html`, не к React-приложению. В `frontend/config.json` задайте абсолютный `apiBase` с префиксом API, например `http://127.0.0.1:8000/api/v1`, и добавьте origin `http://127.0.0.1:5173` в `BB_CORS_ORIGINS` backend. После перезапуска backend выполните:

```bash
python -m http.server 5173 --bind 127.0.0.1 --directory frontend
```

Откройте `http://127.0.0.1:5173/capacity.html`. Порт 5173 нельзя одновременно занимать Vite и этим сервером.

## Конфигурация и AI-ассистент

Backend читает `.env` через `pydantic-settings`; префикс переменных — `BB_`.

| Настройка | Назначение |
|---|---|
| `BB_APP_NAME`, `BB_ENVIRONMENT`, `BB_LOG_LEVEL` | Имя приложения, окружение (`development`, `test`, `production`) и уровень журнала |
| `BB_API_PREFIX` | Префикс API; по умолчанию `/api/v1`, без завершающего `/` |
| `BB_CORS_ORIGINS` | JSON-массив явных HTTP(S)-origin для запросов с другого origin; `*` не разрешён |
| `BB_LLM_BASE_URL`, `BB_LLM_API_KEY`, `BB_LLM_MODEL`, `BB_LLM_TIMEOUT_SECONDS` | Необязательные настройки LLM-провайдера и таймаут |
| `BB_DEV_BACKEND_URL` | Только адрес proxy Vite при разработке; не настройка FastAPI |

Пример включения ассистента с безопасными placeholders:

```bash
BB_LLM_BASE_URL=https://ai.api.cloud.yandex.net/v1
BB_LLM_API_KEY=<api_key>
BB_LLM_MODEL=gpt://<folder_id>/<model_name>
BB_LLM_TIMEOUT_SECONDS=60
```

Ассистент необязателен. Если не задан хотя бы один из `BB_LLM_BASE_URL`, `BB_LLM_API_KEY` или `BB_LLM_MODEL`, его маршруты возвращают HTTP 503 / `LLM_NOT_CONFIGURED`, а остальные backend и интерфейсы продолжают работать. Контекст читается из `backend/jsons/*.json`; ответ LLM является интерпретацией контекста, не наблюдением, прогнозом или сценарным расчётом. После изменения `.env` перезапустите backend. Устройство контекста, ошибки и проверка описаны в [`docs/llm.md`](docs/llm.md).

## API и демонстрационные данные

Ниже перечислены маршруты, реально зарегистрированные в `backend/app.py` и подключённых роутерах. Префикс `/api/v1` показан по умолчанию.

| Маршрут | Что делает |
|---|---|
| `GET /api/v1/health` | Проверяет только процесс API, не готовность данных или моделей |
| `GET /api/v1/config` | Возвращает проектные `supported` и фактически доступные аналитические `available`; сейчас списки истории и прогноза пусты |
| `GET /api/v1/status` | Сообщает `not_connected` для данных, ML и полноценных сценариев; соответствующие capabilities отключены |
| `POST /api/v1/scenarios/capacity` | Возвращает арифметический баланс со статусом `scenario` по пользовательским допущениям за один период |
| `GET /api/v1/llm/summary` | Запрашивает сводку по JSON-контексту |
| `POST /api/v1/llm/ask` | Отправляет вопрос ассистенту |
| `GET /config.json` | Отдаёт frontend только `apiBase`, соответствующий текущему `BB_API_PREFIX`; это не аналитический `/api/v1/config` |
| `GET /`, `GET /capacity` | Отдают `frontend/capacity.html` |
| `GET /app.js`, `GET /frontend/app.js` | Отдают скрипт статического калькулятора |
| `GET /dashboard/` и ресурсы `/dashboard/*` | Раздают собранный `frontend/dist`; без сборки предусмотрен ответ 503 для `/dashboard/` |
| `/docs`, `/redoc`, `/openapi.json` | Стандартная документация FastAPI |

`/api/v1/status` описывает именно интеграцию HTTP-приложения: локальный ML-код или отдельно созданный артефакт сами по себе это состояние не меняют. Существующий расчёт мощности также не делает `capabilities.scenario_analysis` истинным.

Будущие `GET /api/v1/history`, `POST /api/v1/forecast`, `GET /api/v1/scenarios`, `POST /api/v1/scenarios/compare`, `GET /api/v1/sources` и `POST /api/v1/datasets/upload` описаны в [контракте API](docs/api_contract.md), но **не зарегистрированы** и отсутствуют в OpenAPI.

Все числа `frontend/src/demo-fixtures.json` вымышлены и нужны только для проверки отображения. В калькуляторе нагрузка и мощность вводятся пользователем в тоннах за один и тот же период; результат показывает чувствительность, а не прогноз перевозки или доказанный эффект транспортного действия. Пустое значение означает отсутствие данных, а не ноль.

## Проверка

Используйте активное `.venv`; frontend-команды выполняются из корня и не требуют `cd`.

Backend и статический JavaScript (достаточно `.[dev]` и Node.js):

```bash
python -m pytest backend/tests -q
python -m ruff check backend
python -m ruff format --check backend
node --check frontend/app.js
```

Frontend:

```bash
npm --prefix frontend ci --ignore-scripts
npm --prefix frontend run lint
npm --prefix frontend test
npm --prefix frontend run build
```

Полный Python-набор, включая ETL и ML:

```bash
python -m pip install -e ".[dev,data,ml]"
python -m pytest -q
```

Тесты используют синтетические примеры и mock/fake-зависимости; реальный LLM-провайдер не вызывается. Автоматические проверки не заменяют предметную приёмку данных и моделей.

## Данные, ETL, ML и ноутбуки

Эти инструменты не нужны для запуска backend. Исходные файлы, обработанные CSV, модели и отчёты могут отсутствовать после клонирования: `data/raw/`, `data/interim/`, `data/processed/`, `models/` и `reports/generated/` не хранят такой локальный комплект в Git. Для экспериментов нужен переданный проверяемый комплект или локально подготовленные оригиналы.

### Данные и ETL

С локальными файлами в `data/incoming/`:

```bash
python -m pip install -e ".[data]"
python -m pipeline.acquire --local-dir data/incoming
python -m pipeline.build --available-only
python -m pipeline.verify
```

Если оригиналы уже переданы в `data/raw/`, повторный импорт не нужен. `--available-only` разрешает частичную сборку, но не делает её полной; `build` создаёт `candidate_observations.csv`, а не автоматически утверждённый `observations.csv`. Проверка пользовательского CSV: `python -m pipeline.input_check path/to/file.csv`.

Дополнительные комплекты Калининграда, Камчатки и Приморья обрабатываются отдельными модулями. Для вложенных RAR нужна системная libarchive; для повторного извлечения PDF/OSM используются зафиксированные зависимости из `data/requirements-data-lock.txt`. Команды, передача архивов и ограничения: [`data/README.md`](data/README.md) и [подготовка данных](docs/data-preparation.md). Схема пользовательского ввода: [`docs/data-input-guide.md`](docs/data-input-guide.md).

Региональная статистика, перевалка порта, внешняя торговля, транзит, пересечения автомобилей, тарифы и мощность объектов не становятся автоматически тоннажем целевого коридора. Нужно доказать совпадение географии, направления, периода, состава грузов и единицы. Годовой факт не распределяется по месяцам как наблюдение.

### Локальные ML-эксперименты

С подготовленным комплектом данных:

```bash
python -m pip install -e ".[ml]"
python -m pipeline.verify
python -m ml.run --end-year 2030
```

`ml.run` исследует **годовой направленный ряд линии Усть-Луга — Калининград** за 2015–2023, отдельно `inbound` и `outbound`. Это узкая паромная линия, а не весь коридор; цель и методология источника ещё требуют человеческой приёмки.

Другие эксперименты:

```bash
python -m ml.port_run
python -m ml.line_experiment
python -m ml.hypotheses
```

`ml.port_run` отдельно использует **месячный общий каботаж порта Калининград** за 2023–2025: это оценки (`estimated`), восстановленные разностями накоплений, без OD и направлений. Он не заменяет годовой ряд линии и не представляет весь коридор. `ml.sensitivity` строит сценарный HTML-отчёт по уже сохранённой годовой модели без переобучения; порядок запуска, входы и ограничения остальных экспериментов приведены в [`ml/README.md`](ml/README.md).

Успешные запуски создают локальные артефакты в `models/` и отчёты в `reports/generated/`. Функции `ml.forecast` и `ml.forecast_port` читают эти артефакты, но не регистрируют HTTP `/forecast` и не подключают React-интерфейс.

### Jupyter

После подготовки локальных CSV:

```bash
python -m pip install -e ".[data,notebooks]"
python -m jupyterlab notebooks/dataset_overview.ipynb
```

Выберите ядро из `.venv` и выполните **Run → Run All Cells**. Ноутбук обозревает подготовленные данные, не скачивает источники и не выбирает цель модели. Запуск, сохранение HTML и выполненного ноутбука: [`notebooks/README.md`](notebooks/README.md).

## Структура репозитория

| Путь | Назначение |
|---|---|
| `backend/` | FastAPI, настройки, схемы, сценарная арифметика, LLM и HTTP-тесты |
| `frontend/` | Статический калькулятор (`capacity.html`, `app.js`) и React/TypeScript/Vite-приложение (`src/`) |
| `pipeline/` | Импорт оригиналов, ETL, проверки качества и передача комплектов |
| `ml/` | Baseline, временные проверки и отдельные исследовательские эксперименты |
| `data/` | Реестры, примеры схем и локальные исходные/обработанные данные |
| `docs/` | Архитектура, контракты, предметные ограничения и инструкции |
| `tests/` | Общие тесты ETL и ML; HTTP-тесты находятся в `backend/tests/` |
| `notebooks/` | Jupyter-обзоры подготовленных данных |

`frontend/dist/`, `models/` и `reports/generated/` содержат сгенерированные результаты, а не исходную точку запуска. `main.py` — исходный шаблон PyCharm, не точка входа приложения.

Команде ещё предстоит:

1. Выбрать целевой ряд первой версии, его географию, частоту, покрытие и рабочий горизонт; не подменять его более доступным показателем без явного решения.
2. Утвердить два транспортных действия, их механизмы, участки, сроки и подтверждённые диапазоны мощности/времени, CAPEX и OPEX. До этого доступна только чувствительность к пользовательскому вводу.
3. Согласовать модели, временные срезы, метрики, интервалы и допустимые заявления о качестве прогноза.
4. Определить охват логистической цепочки и правила исключения двойного счёта.
5. Зафиксировать обязательный объём интерфейса и выполнить человеческую предметную и визуальную приёмку. Автоматические тесты и подготовленная ИИ документация такой приёмкой не являются.
