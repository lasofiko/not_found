## Подготовка двух локальных частей комплекта от 10.11.2026

С активным Python 3.11+ окружением и зависимостями `[dev,data,ml]`, из корня ветки:

```bash
python -m pipeline.team_bundle --from-processed not_found-data-bundle-2026-11-10-part1-processed --raw-root not_found-data-bundle-2026-11-10-part2-raw --prepare
python -m pipeline.verify
python -m pipeline.reproduce
python -m pytest -q
python -m pipeline.package
```

Каталоги сначала проверяются по внутреннему перечню, затем сохраняется локальный
ZIP-снимок. Код и документы из комплекта не заменяют репозиторий. Результаты —
`data/processed/port_protocol/`: покрытие пяти целей, месячные ряды до декабря
2025, версии публикаций, очередь ручной сверки и отдельный региональный каботаж.
Диагностика сентября хранит только текстовый вывод без чисел.
Эти команды не запускают модели и слепую проверку. SeaNews и производные
передаются только локально. Подробности: [подготовка комплекта](docs/team-bundle-processing.md).


Продукт команды **Not Found**.

Инструмент исследования грузов **между Калининградской областью и основной частью РФ** и транспортных сценариев. История, прогноз и сценарная потребность показываются отдельно. Подтверждённого полного целевого ряда всего коридора пока нет.

В `ml/` есть экспериментальные прогнозы: годовая масса конкретной паромной линии в двух направлениях и месячный каботаж порта по отдельным группам без направлений. Локальные артефакты создаются командами обучения и не входят в Git. Само наличие кода не подтверждает точность. Backend запускается независимо от данных и моделей; прогнозный HTTP API и его отображение в основном интерфейсе ещё не подключены.

## Фиксация месячных моделей и проверка переноса

Перед первым запуском зафиксируйте код и конфигурацию в Git, пересоберите комплект
после изменения файлов его отпечатка и выполните `pipeline.verify` и тесты.
В происхождении модели сохраняются коммит и состояние отслеживаемого кода.

```bash
python -m ml.port_run --all-targets
```

Сначала проверьте выбранный метод, MAE/WAPE относительно naive и пропуски срезов
в `metrics.json` и `backtest.csv` каждого запуска. После фиксации выбора:

```bash
python -m ml.port_run --all-targets --blind-check
```

Эта команда открывает только два нужных выпуска 2026 и создаёт блокировку на
каждую цель. Для новых портов читаются зарегистрированные оригиналы SeaNews,
которые не дополняют обучение. Повтор с тем же состоянием читает сохранённый
результат; незавершённая проверка требует разбора. После просмотра методов и окон
не менять. Сентябрь ранее сверялся: полной независимости проверки не заявляем.
Результаты, ряды и модели остаются локальными.

`python -m ml.hypotheses` пересчитывает исследовательские оценки действий.
Для полной таблицы `action_scenarios.csv` нужен сохранённый **годовой** артефакт
линии `models/latest.json`. Если его нет, после проверки комплекта выполните:

```bash
python -m ml.run --end-year 2030
python -m ml.hypotheses
```

Календарь отделяет факт ремонта «Амбала» от планового возврата «Балтийска».
Резерв рассчитывается отдельно по годам календаря; без календаря эффект пустой.
Предел ж/д части применяется только к оценённой массе груза в вагонах.
Месячные модели и слепая проверка при этом не запускаются.
Основные действия для линии: А — резервный паром на время ремонтов, Б — сокращение портовой части оборота.
Дальневосточные порты проверяют перенос процедуры; параметры CAPEX/OPEX остаются открытыми.

## Быстрый запуск

Нужен Python 3.11+.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -e ".[dev]"
Copy-Item .env.example .env
uvicorn backend.app:app --reload
```

Откройте `http://127.0.0.1:8000` (калькулятор мощности). React-демо после сборки и перезапуска backend: `http://127.0.0.1:8000/dashboard/`. Для сборки нужен Node 22.12+ или 24: `npm --prefix frontend ci --ignore-scripts`, затем `npm --prefix frontend run build`. Все числа React-демо синтетические; модель не вызывается. Swagger: `http://127.0.0.1:8000/docs`. При совместном размещении страница читает `GET /config.json`: backend отдаёт фактический `BB_API_PREFIX`, поэтому после изменения префикса и перезапуска сервера JavaScript править не нужно. Этот маршрут отличается от аналитического `/api/v1/config`.

Для отдельного размещения Frontend отредактируйте `frontend/config.json`: укажите абсолютный базовый URL backend с префиксом API, например `{"apiBase":"http://127.0.0.1:8000/api/v1"}`. Запустите из корня репозитория `python -m http.server 5173 --directory frontend` и откройте `http://127.0.0.1:5173/capacity.html`. Добавьте точный origin `http://127.0.0.1:5173` в JSON-массив `BB_CORS_ORIGINS`, затем перезапустите backend. Для другого `BB_API_PREFIX` обновите только `apiBase` в файле отдельного Frontend. Если конфигурация или API недоступны, страница показывает сообщение об ошибке и не отправляет расчёт без настроенного адреса.

`GET /api/v1/health` возвращает `service: not-found-backend` и проверяет только работу сервера. `GET /api/v1/config` отдаёт проектные варианты отдельно от реально доступных функций. `GET /api/v1/status` сообщает, что данные, ML и полноценные сценарии ещё не подключены: `components.ml: not_connected`, `capabilities.forecast: false`. Это состояние HTTP-приложения сохраняется и при наличии локального кода или отдельно созданной модели. Примеры:

```powershell
Invoke-RestMethod http://127.0.0.1:8000/api/v1/health
Invoke-RestMethod http://127.0.0.1:8000/api/v1/config
Invoke-RestMethod http://127.0.0.1:8000/api/v1/status
```

Существующий `POST /api/v1/scenarios/capacity` и главная страница сохранены. Они считают только чувствительность дефицита мощности к **введённым пользователем** значениям, без модели или проверенного грузопотока. Поэтому `status.capabilities.scenario_analysis` остаётся `false`.

Будущие `/history`, `/forecast`, `/scenarios`, `/scenarios/compare`, `/sources` и `/datasets/upload` описаны в [контракте API](docs/api_contract.md), но маршруты пока не зарегистрированы.

Проверка Backend с группой зависимостей `dev`:

```powershell
python -m pytest backend/tests -q
python -m ruff check backend
python -m ruff format --check backend
node --check frontend/app.js
cd frontend
npm ci --ignore-scripts
npm run lint
npm test
npm run build
cd ..
```

Полный набор, включая ETL и ML, требует дополнительных зависимостей:

```powershell
python -m pip install -e ".[dev,data,ml]"
python -m pytest -q
```

Проверка таблицы наблюдений: `python -m pipeline.validate data/processed/observations.csv`. Пока файла нет, команда сообщит об этом: исходные данные не скопированы в репозиторий автоматически.

## Локальные ML-эксперименты

На Linux/macOS из корня проекта, с подготовленным локальным комплектом (Python 3.11+):

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e ".[ml]"
python -m pipeline.verify
python -m ml.run --end-year 2030
```

Если `.venv` уже существует, повторно создавать его не нужно. В новом терминале сначала выполните `source .venv/bin/activate`; без активации используйте `.venv/bin/python` вместо `python`. На Windows PowerShell активация: `.\.venv\Scripts\Activate.ps1`.

`ml.run` реализует годовой прогноз линии Усть-Луга — Калининград: по девять наблюдений 2015–2023 отдельно для `inbound` и `outbound`. Три метода (`naive`, `drift`, `ses`), выбор по 2020–2021, отдельная проверка 2022–2023, итоговое обучение на 2015–2023. При успешном запуске прогноз 2024–2030 и модельные интервалы сохраняются в `reports/generated/ml/<версия>/`, переносимый JSON модели — в `models/<версия>/`. Оба каталога вне Git. Последний факт — 2023; модель не описывает весь коридор и не доказывает точность до 2030.

Отдельные команды с тем же подготовленным комплектом и активным окружением:

```bash
python -m ml.port_run
python -m ml.line_experiment
```

`ml.port_run` следует [протоколу 10.11.2026](docs/ml-port-evaluation-protocol.md): основная цель — грузы на паромах порта Калининград, 43 месяца с июня 2022 по декабрь 2025, статус `estimated`. Кандидаты: naive, seasonal_naive, drift, ses; Ridge исключена из сравнения. `--target kaliningrad_containers` и `--target kaliningrad_total` выбирают другие группы; `--all-targets` запускает доступные цели и сообщает об отсутствующих. Во входном processed-комплекте ряды каботажа двух дальневосточных портов отсутствуют. Указатели разделены по `models/port/<target_id>/`, отчёт — `reports/generated/ml-port/<версия>/report.html`. Слепые итоги 2026 открываются только отдельным `--blind-check` после фиксации модели. Разности не подменяют годовой направленный ряд линии. `ml.line_experiment` требует первичного HTML для расширения годовой истории и сохраняет самостоятельную годовую модель.

После создания или получения проверенного артефакта функции для Fullstack доступны через `from ml import forecast, forecast_port`: `forecast(direction="inbound", end_year=2030)` и `forecast_port(end_period="2026-12")`. Для обратного направления линии — `outbound`; у каботажа `direction: null`. Без артефактов эти вызовы отклоняются. Они не регистрируют HTTP `/forecast`; интеграция следует [контракту API](docs/api_contract.md). Полная инструкция, протокол, выходы и проверки: [ML README](ml/README.md).

Интерактивный отчёт о влиянии параметров: `python -m ml.sensitivity`. Для него нужен уже сохранённый годовой артефакт; переобучение не требуется. Команда напечатает путь к автономному `report.html`: откройте его браузером. Выбор направления/года и три регулятора показывают изменение дефицита и запаса провозной возможности. Нагрузка, исходная возможность и её прибавка — сценарные допущения в процентах от базового прогноза; это не измеренная мощность или обученное влияние факторов. Расчёты, сравнение примеров и CSV/JSON сохраняются отдельно в `reports/generated/sensitivity/`.

Реестр оригиналов: [data/source_registry.json](data/source_registry.json). Каталог из Google-таблицы: [data/source_catalog.csv](data/source_catalog.csv). Исследуется **весь грузовой коридор по четырём видам транспорта**. Полного сопоставимого целевого ряда пока нет.

Для присланных файлов в `data/incoming/` (экспортные XLSX, транзитный XLS, объединённый Excel и два ZIP), с активным Python 3.11+ окружением:

```bash
python -m pip install -e ".[data,notebooks]"
python -m pipeline.acquire --local-dir data/incoming
python -m pipeline.build --available-only
python -m pipeline.verify
python -m jupyterlab notebooks/dataset_overview.ipynb
```

После установки зависимостей этот путь работает офлайн. Внутренние манифесты ZIP и SHA-256 проверяются; одинаковые вложения не размножаются. `--available-only` перечисляет отсутствующие источники в манифесте; порча существующего оригинала останавливает сборку. Повторный импорт восстанавливает файлы без дублирования паспортов. Исходники с читаемыми именами находятся в `data/incoming/`; рабочие неизменяемые копии — в `data/raw/`. Обе папки исключены из Git. В распакованном архиве передачи с заполненным `data/raw/` повторный импорт не требуется.

Результаты: [грузовой срез региона](data/processed/regional_freight.csv), [частичные транспортные показатели](data/processed/supplemental_freight.csv), [портовый каботаж с января](data/processed/port_cabotage_cumulative.csv), [оценки месячных разностей](data/processed/port_cabotage_monthly.csv), [пересечения грузовиков](data/processed/border_crossings.csv), [карта покрытия](data/processed/freight_coverage.csv). Полный региональный набор — `regional_indicators.csv`, диагностика — `supplemental_issues.csv`; реальные CSV остаются вне Git. [Качество и ограничения](docs/supplemental-quality.md), [что вам сделать сейчас](docs/data-engineer-next-steps.md).

Первоисточник Росморпорта получен: `candidate_observations.csv` содержит **18 годовых строк за 2015–2023**, по девять на направление узкой паромной линии. Все 18 значений автоматически сверены с предоставленным CSV из ZIP — совпадают. `context_observations.csv` содержит 18 строк терминальных итогов/каботажа, `coverage.csv` — четыре ряда покрытия. Человеческая проверка методики и выбор цели остаются открытыми.

На другой машине для заполнения кандидата нужны сохранённые оригиналы из архива передачи либо получение страницы: `python -m pipeline.acquire --source rosmorport_freight`, затем `python -m pipeline.build --available-only`. При отсутствии страницы этот файл содержит только заголовок; копия из ZIP остаётся отдельно в `supplemental_freight.csv`.

Строгое воспроизведение по **всем зарегистрированным оригиналам**, если они переданы:

```bash
python -m pipeline.acquire
python -m pipeline.build
python -m pipeline.verify
python -m pipeline.validate data/processed/candidate_observations.csv --registry data/source_registry.json --corridor --require-observations --observed-only
python -m unittest discover -s tests -v
python -m pipeline.package
```

`acquire` нужен только для получения отсутствующих оригиналов (интернет); сохранённые оригиналы проверяются по хешу. Если дополнительный источник недоступен, команда возвращает ошибку, сохраняя успешно полученные файлы; обязательные для сборки источники перечислены в инструкции. По переданным оригиналам `build` и `verify` работают **офлайн**. Для старого XLS нужен `xlrd==2.0.2`: в комплект уже включён официальный wheel с проверяемым SHA-256; при отдельной установке используйте `pip install -e ".[data]"`. Остальные таблицы читаются стандартной библиотекой. Существующий `observations.csv` не перезаписывается. Справочные показатели, параметры объектов и факторы хранятся отдельно. Локальный ZIP передачи создаётся в игнорируемой Git папке `reports/generated`, без внешней публикации.

Покрытие, варианты цели, ошибки источников и участие ИИ: [аудит](docs/data-audit.md). Полная инструкция, правила очистки и приёмка человеком: [подготовка и передача](docs/data-preparation.md).

- [export_growth_checks.csv](data/processed/export_growth_checks.csv) — 3 384 проверки опубликованных индексов; [table_quality.json](data/processed/table_quality.json) — машинный отчёт. Понятное описание преобразований, пропусков и спорных мест: [качество новых таблиц](docs/tables-quality.md).

В экспортных файлах **только январь 2021 и январь 2022**, а виды экспорта вложены друг в друга. Это внешняя торговля регионов, без подтверждённого соответствия перевозкам нужного коридора. Транзитный XLS содержит выборку товарной группы 2204 (вино); принадлежность Калининградскому коридору не установлена. Эти таблицы сохраняются отдельно от кандидата целевого ряда.

Обработка сохраняет пропуски, переводит кг в тонны и тыс. USD в USD, проверяет ключи, даты и индексы роста. Из очищенного транзита исключены реквизиты участников и транспорта; товары связываются хешем декларации. Оригинал с этими реквизитами остаётся локальным и включается в ZIP, который следует передавать согласованным получателям. Ссылка на публикацию и методика четырёх файлов пока не установлены.

Повторная обработка текущего комплекта: `python -m pipeline.build --available-only`, затем `python -m pipeline.verify`. Как импортировать такие файлы на другой машине: [инструкция](docs/data-preparation.md#импорт-пользовательских-таблиц).

## Структура

| Каталог | Назначение |
|---|---|
| `docs/` | Договорённости, контракты и инструкции подготовки данных |
| `data/raw/` | Неизменённые первоисточники, локально |
| `data/interim/` | Промежуточные преобразования, локально |
| `data/processed/` | Проверенные таблицы для модели, локально |
| `data/examples/` | Малые примеры схем без вымышленных целевых фактов |
| `pipeline/` | Проверка и последующая сборка наборов |
| `ml/` | Код годового прогноза линии, месячного каботажа и временной проверки; инструкции в `ml/README.md` |
| `backend/app.py` | Создание приложения, CORS, статический интерфейс |
| `backend/api/v1/` | HTTP-маршруты и существующий расчёт чувствительности |
| `backend/schemas/` | Типизированные запросы и ответы |
| `backend/core/` | Настройки и ошибки |
| `backend/scenarios.py` | Общая арифметика баланса для API и отчёта чувствительности |
| `backend/tests/` | Контрактные HTTP-проверки |
| `frontend/` | Статическая страница без отдельной сборки |

Исходный `main.py` оставлен без изменений. Материалы кейса находятся в отдельной папке `кейс чемпионат/outputs`; их нужно подключать через реестр источников, а не переносить все файлы в Git.

Предложения к обсуждению цели, проверки прогноза и логистической цепочки: [вопросы команды](docs/team-discussion.md).

## Следующие решения команды

1. Выбрать проверяемый целевой ряд и его частоту; подтвердить, можно ли получить месячные тонны по нужной паре регионов.
2. Утвердить две гипотезы действий и подтверждённые диапазоны мощности, сроков, CAPEX/OPEX.
3. Выбрать модели и временные срезы проверки; решить охват логистической цепочки.
4. Зафиксировать обязательный объём интерфейса к сдаче и горизонт (2030 или гибкий до 2035).

Backend расширяется после приёмки данных, модели и сценарных параметров. При подключении соответствующие признаки в `/config` и `/status` должны определяться реальной доступностью, а не оставаться текущими значениями. Разработку каркаса и документации выполнил ИИ; человеку нужно проверить схемы, происхождение будущих чисел, запустить команды проверки и согласовать открытые решения перед сдачей.

Подробности: [контракты](docs/contracts.md), [план команды](docs/team-plan.md).
