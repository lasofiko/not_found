# Текущая архитектура

## Итоговая интеграция месячных моделей (12.11.2026)

React `PortForecastPanel` → `/port-forecasts` → `PortForecastService` →
`ml.port_predict` → проверенные сохранённые JSON в `models/port/<target_id>/`.
`backend/site_models.json` закрепляет версии пяти целей и режимы показа;
`docs/final/site-*.csv` связывают метрики с этими версиями. Основная цель —
паромы Калининграда, Ridge AR(3) `bb-ridge-d9c6acb34f45` на исходной истории.
Петропавловск возвращает только историю, Владивосток — предупреждение.
Синтетические заполнения остаются в отдельном исследовании.

Новые HTTP-запросы не обучают модель и не открывают исходные слепые данные.
API передаёт происхождение артефакта, версии, календарь и статусы; UI показывает
расчётную историю отдельно от прогноза, условный 80% интервал и источники.
Годовая направленная линия и её API сохраняются как дополнение; портовые
группы не суммируются с линией и не получают вымышленных направлений.
Dockerfile включает итоговые CSV, Compose монтирует модели только для чтения.
`scripts/smoke.py` проверяет портовый каталог и при наличии моделей прогноз;
эта же проверка используется существующим контейнерным CI.

Актуальные обозначения: А — резерв, Б — портовый оборот, В — постоянный
дополнительный паром. Форма сравнения рассчитывает чувствительность А/В.
Исторические описания прежних решений ниже сохраняют контекст своих версий.

Отдельный синтетический контур v0.1: `pipeline.synthetic_inventory` читает весь
предоставленный снимок и вложения; `synthetic_inputs` повторно извлекает выбранные
портовые ячейки; новые `ml.synthetic_methods` и `ml.synthetic_evaluation` выполняют
изолированный эксперимент. Прежние модули моделей, артефакты и указатели не меняются.
Выход — самостоятельный комплект в `reports/generated`, с оригиналами выбранных
источников, версиями, кодом, метриками и ZIP. `backend.synthetic_data.SyntheticStore`
читает его только при явном `BB_SYNTHETIC_PATH`, проверяет SHA-256 и схему, кэширует
проверенный комплект с инвалидированием по изменению файлов. `/synthetic/*` обслуживает
фильтры, реализации, раздельные характеристики, происхождение и экспорт без обучения.
Оптимистичный и стрессовый варианты требуют численного пользовательского допущения;
без него возвращается `requires_input`, а не вымышленные реализации.
Основной React не меняется. [Методика и передача](synthetic-generation.md).

Сравнение решений v0.19: сервер создаёт неизменяемый снимок в ограниченном
кэше процесса (128 записей, 30 минут). Снимок включает общий контекст, результаты
`capacity_balance`, пороги, паспорта и необязательный профиль направлений.
Экспорт и AI принимают только идентификатор снимка. Смена модели/данных делает
связанный снимок недействительным. Новый контур не обучает и не изменяет модели.
React отменяет связанные запросы при редактировании входа. Подробный AI-разбор —
фиксированные три вызова существующего клиента, координация обычным asyncio;
база данных, очередь и новый agent framework не требуются. Один серверный worker.
Точный контракт: [сравнение решений](contracts.md#сравнение-решений-v019-12112026).

Изменения 12.11.2026: проверка React-сборки выполняется в рабочем потоке под
асинхронной блокировкой. Полный SHA-256 исходников пересчитывается максимум
раз в 0,5 секунды; замена манифеста/HTML инвалидирует кэш сразу. Health/API
работают во время проверки и при отсутствии/порче UI.

Ассистент ограничен серверным Bearer-токеном при сетевом размещении и в production,
общей частотой, параллельностью и длиной ответа. Локальный development не требует
аккаунтов. Одинаковые сводки кэшируются по полному проверенному контексту;
кэш также проходит ограничения доступа и частоты. Несколько процессов имеют
независимые лимиты и кэши.

Сборка таблиц и моделей готовит отдельное проверенное поколение, затем атомарно
переключает указатель. `data/current.json` выбирает `.generations/data/<version>`;
без указателя сохраняется прежний способ чтения. CSV в корне — совместимая копия,
а не точка фиксации. Опубликованные версии моделей не перезаписываются.
Одна рабочая копия допускает одного писателя: файловая блокировка процесса
охватывает подготовку, проверку, указатель и совместимую копию. ОС освобождает
её при аварийном завершении. Имя ZIP и его содержимое выбираются из одного
зафиксированного снимка, включая восстановление после прерванной копии.

## Инфраструктура запуска

`Dockerfile`: Node 24.14.0 (`npm ci`, TypeScript + Vite) → Python 3.11
(`uv sync --locked`, только серверные зависимости). В runtime нет Node, npm,
pytest, исходных выгрузок и ключей. Исходники React сохраняются для проверки
build-info; `dist` берётся из стадии сборки. Процесс UID/GID 10001.

`compose.yaml` содержит один сервис `app`: браузер → `127.0.0.1:8000` →
FastAPI (`backend.app:app`) → проверенный JSON в `/app/models`; при настроенном
LLM сервер обращается к внешнему Chat Completions API. React получает относительный
API-префикс через `/config.json`; Docker hostname браузеру не передаётся.
Том моделей и корневая ФС доступны только для чтения, `/tmp` — tmpfs.
ETL и обучение выполняются отдельно, в этот контейнер не вынесены.

Vite dev на 5173 проксирует API к 8000 через `BB_DEV_BACKEND_URL`.
Streamlit, Steam, Nginx, БД, Redis, отдельный ML-worker и CD в коде не обнаружены.
GitHub Actions проверяет lock, backend, React, HTTP smoke и контейнер с двумя
API-префиксами; публикация и развёртывание не выполняются.

Единственный основной интерфейс — существующий React FloCast с контейнеровозом,
светлой темой по умолчанию, Sidebar, показателями, транспортом, картой и AI-панелью.
Точка входа frontend/index.html → src/main.tsx → App.tsx. Палитра, App.css,
index.css, типографика и фотографии сохраняются.

Vite обслуживает React на http://127.0.0.1:5173/ с base=/ и проксирует
/config.json и фактический BB_API_PREFIX к backend. FastAPI непосредственно
раздаёт production-сборку этого же React на http://127.0.0.1:8000/ .
/dashboard/ — старая ссылка на корень. /capacity и /capacity.html ведут в
/#capacity, где CapacityCalculator.tsx вызывает прежний сценарный API.
Архивные capacity.html/app.js не образуют отдельную главную страницу.

backend/frontend.py обеспечивает проверку build-info.json, SHA-256 исходников
и index.html, SPA fallback и отсутствие кэширования HTML. API, конфигурация и
документация зарегистрированы раньше статической раздачи; неизвестный API
сохраняет JSON 404, неверный метод известного маршрута — 405. Без актуальной
сборки UI отвечает 503 с командой build, API продолжает работать. Новый dist
обнаруживается без перезапуска. HTML исключён из PWA precache.

React → FastAPI → ForecastService → существующий ml.predict.forecast.
Модель проверяется по указателю, SHA-256, схеме и протоколу; в HTTP-запросе не
обучается. Графики, таблица и CSV используют реальный ответ в тоннах за год,
с версиями и ограничениями. Отдельное существующее демо маркируется synthetic.
Неподключённая география не получает вымышленных чисел.

Калькулятор React → прежний POST /api/v1/scenarios/capacity →
backend.scenarios.capacity_balance. Арифметика не дублируется в React.
Реестр действий определяет А как резерв на ремонты, Б — постоянный паром;
их эффекты не подменяются числами демонстрации.

AI-панель → /api/v1/llm/* → настроенный LLM-провайдер. Ключи остаются на сервере.
Без настроек показывается явная недоступность; прогноз и калькулятор работают.
AskTransportAssistant получает ForecastService через порт и передаёт провайдеру
проверенный ForecastResponse выбранного направления. Этот же снимок возвращается
в `context` ответа вместе с `result_type: interpretation`. Демонстрационные JSON
не подключены. Неподдержанная география и повреждённая модель не вызывают LLM.

## Исследовательские модули из main

Экспериментальный `ml/` реализует годовой прогноз конкретной паромной линии в обоих направлениях. `ml.run` проверяет снимок данных, сравнивает три метода во временных срезах и сохраняет JSON-параметры, прогнозы и отчёт. `ml.forecast` предоставляет Fullstack переносимый результат со статусом forecast и явными ограничениями; годовой результат подключён к HTTP и React через ForecastService. Региональные ряды, приблизительные месячные сводки и сценарная потребность автоматически в эту цель не попадают.

Отдельный `ml.port_run` использует `pipeline.port_protocol` и протокол 10.11.2026: пять отдельных целей, для трёх калининградских групп 43 месячные разности с июня 2022 по декабрь 2025. Поздние пересмотры не заменяют первую доступную сопоставимую разность. Временные срезы маскируют будущие публикации. Сравниваются naive, seasonal_naive, drift и ses; выбор июль 2024 — июнь 2025 отделён от проверки июль — декабрь 2025. Отсутствующие ряды портов Дальнего Востока не подменяются региональной статистикой. `ml.forecast_port` читает отдельные JSON по цели, направление и OD не назначаются. Слепая проверка 2026 запускается явно после выбора и сохраняется один раз. `ml.line_experiment` требует первичного HTML и остаётся отдельным исследованием.

`pipeline.team_bundle` импортирует предоставленный processed-ZIP с проверкой всех вложений, сохраняет оригинал и предыдущие локальные результаты. Сборка `provided_processed` заново сериализует предоставленные CSV и выпускает новый манифест; проверка сверяет значения с исходным ZIP, хеши текущего кода и единицы. Первичные raw-источники не объявляются проверенными. Строгий режим исходного конвейера сохранён. Дополнения, реестр их происхождения и конфликты обрабатываются отдельно; пресс-релизы, расписания и report_only не добавляются в обучающую цель.

`pipeline.acquire_list` получает дополнительные оригиналы из реестра DOCX по `additional_sources.json`; `extended_extract` извлекает новые однородные наборы, `extended` оценивает каждый источник и готовит покрытие/диагностику. Исторические SeaNews дополняют портовые таблицы в `supplemental`. БЖД, Храброво, погода, экономические показатели, камера границы, OSM и пассажирская сеть сохраняют свой охват; они не включаются автоматически в цель линии или обучение. Версии PDF/OSM-обработчиков входят в отпечаток сборки, wheel-зависимости — во внутренний пакет для офлайн-воспроизведения.

`ml.sensitivity` выпускает отдельный автономный HTML-отчёт по сохранённой модели. Общая арифметика баланса нагрузки находится в `backend/scenarios.py` и используется также сценарным API. Python готовит сетку сочетаний пользовательских допущений; `frontend/sensitivity_report.html` отображает готовые строки, график и карту дефицита без повторения расчётной логики. Проценты берутся от прогноза только как от масштаба демонстрации. Статусы, входные допущения, версии и границы направленного годового охвата сохраняются. Прогноз не переобучается, сценарии не включаются в факты/backtest.

Наблюдаемая масса — уникальный груз через границу коридора. Нагрузка на морской и железнодорожный участки может учитываться отдельно, но вагон на пароме не должен попадать вторым грузом в сухопутный транзит. Уровни детализации: коридор → направление → вид → категория → маршрут/участок при наличии данных. Нельзя агрегировать несовместимые годы, категории и определения.

Временная гранулярность следует за наблюдениями: месяц предпочтителен, год допустим для подтверждённого узкого ряда. Неполный 2026 год явно маркируется. Для 2027–2030 будущие факторы задаются сценарием либо отдельно прогнозируются; исторический backtest не получает будущих фактов.

Визуализация должна раздельно показывать факт, прогноз с интервалом и сценарную потребность; фильтры по направлению, виду, категории и горизонту; таблицу происхождения цифр; предупреждения о покрытии. Экономика, надёжность и экология включаются только при наличии коэффициентов с датой и источником.

## Географический выбор трёх коридоров

По решению пользователя интерфейс поддерживает Калининградскую область,
Приморский край и Камчатский край в обоих направлениях относительно остальной
России. Географический справочник frontend не является источником грузовых
наблюдений. Для выбранных городов и новых коридоров модель/API не подключены;
вместо старого числового демо выводится отсутствие данных. Демо Калининграда
сохранено только на прежнем агрегированном охвате. Поля выбора и источники:
`frontend/GEOGRAPHY.md`.
