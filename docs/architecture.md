# Архитектура первого этапа

Поток: **исходник → реестр и проверка → нормализованное наблюдение → baseline/модель → API → интерфейс**. Отдельная ветвь: **вводимые параметры действия → сценарный расчёт → сравнение**. Модули общаются через контракты в `docs/contracts.md`; модель не читает файлы интерфейса, интерфейс не вычисляет прогноз.

Начинаем с одного Python-сервиса и статического интерфейса: так команда может показать работающую цепочку без второго сервера и сборщика. Если потребуются сложные карты или графики, `frontend/` можно вынести в самостоятельное приложение без изменения API. Отдельная база пока не нужна: версионированные CSV/Parquet и манифест достаточны для прототипа. Переход к БД оправдан при многопользовательских загрузках и сохранении сценариев.

Два режима: подготовленный Калининградский набор и загрузка своей таблицы по тому же контракту. Загрузка появится после принятия реального целевого ряда и проверки защиты от неверной географии и единиц. Сейчас API выполняет только проверяемый арифметический расчёт сценария; прогнозный endpoint не выдуман.

Экспериментальный `ml/` реализует годовой прогноз конкретной паромной линии в обоих направлениях. `ml.run` проверяет снимок данных, сравнивает три метода во временных срезах и сохраняет JSON-параметры, прогнозы и отчёт. `ml.forecast` предоставляет Fullstack переносимый результат со статусом forecast и явными ограничениями; подключение HTTP/frontend выполняется отдельно. Региональные ряды, приблизительные месячные сводки и сценарная потребность автоматически в эту цель не попадают.

Отдельный `ml.port_run` использует `pipeline.model_inputs` для 36 месячных разностей портового каботажа, не изменяя существующий ETL-комплект. Сравнительные колонки 2023 и основные годы 2024–2025 сохраняют роли, ячейки и оценку доступности по месяцу размещения URL. Временные срезы маскируют ещё не опубликованные значения; Ridge обучает лаг, среднее и календарные признаки только внутри окна. Доступ до целевого месяца проходит рекурсивно. `ml.forecast_port` читает независимый JSON с сохранёнными интервалами из `models/port/`; направление и OD не назначаются. `ml.line_experiment` сравнивает длину годовой истории и раздельный/агрегатный подходы в отдельном отчёте, не заменяя существующую модель.

`pipeline.acquire_list` получает дополнительные оригиналы из реестра DOCX по `additional_sources.json`; `extended_extract` извлекает новые однородные наборы, `extended` оценивает каждый источник и готовит покрытие/диагностику. Исторические SeaNews дополняют портовые таблицы в `supplemental`. БЖД, Храброво, погода, экономические показатели, камера границы, OSM и пассажирская сеть сохраняют свой охват; они не включаются автоматически в цель линии или обучение. Версии PDF/OSM-обработчиков входят в отпечаток сборки, wheel-зависимости — во внутренний пакет для офлайн-воспроизведения.

`ml.sensitivity` выпускает отдельный автономный HTML-отчёт по сохранённой модели. Общая арифметика баланса нагрузки находится в `backend/scenarios.py` и используется также сценарным API. Python готовит сетку сочетаний пользовательских допущений; `frontend/sensitivity_report.html` отображает готовые строки, график и карту дефицита без повторения расчётной логики. Проценты берутся от прогноза только как от масштаба демонстрации. Статусы, входные допущения, версии и границы направленного годового охвата сохраняются. Прогноз не переобучается, сценарии не включаются в факты/backtest.

Наблюдаемая масса — уникальный груз через границу коридора. Нагрузка на морской и железнодорожный участки может учитываться отдельно, но вагон на пароме не должен попадать вторым грузом в сухопутный транзит. Уровни детализации: коридор → направление → вид → категория → маршрут/участок при наличии данных. Нельзя агрегировать несовместимые годы, категории и определения.

Временная гранулярность следует за наблюдениями: месяц предпочтителен, год допустим для подтверждённого узкого ряда. Неполный 2026 год явно маркируется. Для 2027–2030 будущие факторы задаются сценарием либо отдельно прогнозируются; исторический backtest не получает будущих фактов.

Визуализация должна раздельно показывать факт, прогноз с интервалом и сценарную потребность; фильтры по направлению, виду, категории и горизонту; таблицу происхождения цифр; предупреждения о покрытии. Экономика, надёжность и экология включаются только при наличии коэффициентов с датой и источником.
